# pair-wise-yf-47 城市轨道交通突发停运应急协同

滨江站积水后，调度员、车站值班员、公交接驳负责人共用同一张可离线续作的处置账。

## 处置账规则（`lib/ledger/`）

所有业务规则收敛在纯函数引擎 `lib/ledger/engine.ts`，UI/Zustand 只是它的外壳，便于单测与离线续作。

1. **车站—区段通行闸门**：区段内任一车站未恢复（封闭/限流/恢复中），该区段不能放行；调度员的放行请求被拦截后留在重试队列，待车站全部恢复时自动重放。已放行区段若有关联车站再次变化，放行自动收回。恢复只解除拦截，放行仍需调度员显式确认。
2. **变化即作废重算**：接驳计划的经停车站或车辆数一变，双岗会签（调度员 + 公交接驳负责人）与车辆占用全部作废，计划退回草稿，重新申请车辆、重新会签。
3. **车辆池先到先得**：车辆申请按提交时刻取全局排队序号（同毫秒也严格保序），先到者占用；队首需求不满足时后续一律排队，不允许插队；占用释放后按 FIFO 自动递补。
4. **离线续作与依赖合并**：断网期间操作照常在本地入账，每条操作携带**岗位**（`role`）、**基线**（`baseVersion` 乐观并发）和**依赖**（`dependsOn`）。恢复联网后发件箱按到达顺序做不动点合并——依赖满足才生效；同一操作号只生效一次（重复提交按去重处理）；**越权、缺依赖、基线过期、业务条件不满足**的操作留在重试队列，可按当前账重试或放弃。

操作类型：`station.status` / `section.release` / `plan.upsert` / `plan.submit` / `plan.sign` / `plan.execute`。
岗位权限：车站状态仅车站值班员；区段放行与计划执行仅调度员；建改计划、提交会签仅公交接驳负责人；会签由调度员与接驳负责人双岗完成。

## 文件结构

- `lib/ledger/types.ts`：领域模型与操作协议
- `lib/ledger/engine.ts`：纯函数引擎（闸门、作废重算、FIFO 占用、依赖合并、重试队列）
- `lib/ledger/selectors.ts`：页面用视图选择器
- `lib/ledger/engine.test.ts`：10 个引擎单测
- `lib/ledger/store.e2e.ts`：断网→恢复全流程演练
- `store/ledger.ts`：Zustand 持久化 store（发件箱 + 单调到达时钟 + 依赖自动挂接）

## 本地运行

```bash
npm install
npm test     # 10 个引擎单测 + 1 个断网恢复端到端演练
npm run dev  # 端口 62012
```

工作台可在右上角切换「在线/断网」与岗位，左侧四个面板：总览（车站+态势图）、区段通行（放行闸门）、接驳会签（车辆占用与双岗签署）、离线处置账（流水/发件箱/重试队列/作废操作号）。
